# Управление версиями клиентов

Политика версии является подписанными данными, а не удалённым исполняемым кодом.

## Порядок обычного релиза

1. Сначала Build Factory создаёт и проверяет артефакт.
2. Release проходит production gate и публикуется.
3. В «Релизы → Политика версий» задаётся recommended version.
4. Rollout начинается с 5–10%.
5. После наблюдения rollout повышается ступенчато.
6. Minimum supported version изменяется только после полного устойчивого rollout.

## Аварийная блокировка

Если конкретная клиентская версия создаёт критический риск:

1. сначала должен существовать опубликованный исправленный артефакт;
2. исправленная версия указывается как recommended;
3. плохая версия добавляется в blocked_versions;
4. официальные клиенты запрещают новые подключения на плохой версии;
5. уже работающий Android/iOS/browser transport не обрывается принудительно только из-за появления policy, чтобы не создавать дополнительный outage или browser DIRECT leak.

Сервер не позволит сохранить blocking policy без опубликованного пути обновления.

## Staged rollout

Когорта вычисляется детерминированно из:

`device_id + target + recommended_version`.

Поэтому один пользователь не перескакивает между «есть обновление / нет обновления» при каждом запуске.
