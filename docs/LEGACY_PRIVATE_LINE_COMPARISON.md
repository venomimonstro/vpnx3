# Сравнение VPNX3 с работавшим Private-line-tg-claude
Дата: 2026-10-10. Аудит выполнен по репозиториям
`venomimonstro/Private-line-tg-claude` (ветка `claude/private-line-mvp-cmx4Z`)
и `venomimonstro/vpnx3` (`main`).

## Главное отличие транспортного пути

| | Private-line | VPNX3 |
|---|---|---|
| VPN-демон | Xray через Marzban | отдельный Xray с локальным root-only менеджером |
| Публикация | Docker `network_mode: host`, Xray напрямую на TCP/443 | Docker bridge, опубликован TCP/8443, вариант 2053 |
| Владелец публичного 443 | Xray, на отдельной VPN-ноде | Caddy с HTTPS админки |
| REALITY | SNI `www.microsoft.com`, Xray VLESS TCP + Vision | SNI `dl.google.com`, Xray VLESS TCP, Vision или совместимый iOS без flow |
| Клиенты | динамические профили Marzban, конфиг/hosts из живого API | профили в конфиге Xray; формирование ссылок в менеджере |
| Восстановление | circuit breaker + pending queue + subscription watchdog | Docker restart + systemd и локальные проверки; нет независимого RF-клиентского мониторинга |

**Гипотеза №1 по реальным симптомам:** старый сервис достигался через TCP/443,
а текущий на мобильной сети не послал ни одного SYN на 8443 (два наблюдения).
Это не доказывает блокировку 8443: возможно некорректное импортирование или
маршрутизация клиента, но это основное проверяемое отличие.

Другой SNI сам по себе не делает старую конфигурацию лучше. Нельзя наугад
переключать `dl.google.com` на `www.microsoft.com`: сначала проверить
REALITY target с конкретной ноды и сохранить ключи.

## Что уже перенесено из проверенных решений

- **Fail-closed выдача VLESS-профилей** как в старом `app/vpn/marzban.py` и
  `app/services/vpn_key.py`: проверка готовой URI по реальным UUID,
  `pbk`, `sid`, SNI, `fp`, порту, TLS REALITY и `flow`. Повреждённая
  ссылка не выдаётся из админки и не сохраняется при создании. Для iOS
  отсутствующий `flow` считается корректным (в отличие от старого
  Android-oriented `check_key_health`).
- **Регрессионные проверки ссылки** по аналогии с прежним watchdog; без
  скрытых автоперевыпусков UUID или X25519 ключей.
- **Отдельная VPN-нода с прямым TCP/443:** `scripts/install-vpn-edge-443.sh`
  повторяет рабочую топологию без запуска Marzban или публичного API. На
  существующем control VPS со занятым 443 он откажется стартовать.
- Доступность `telegram.org` проверяется настоящим Xray-клиентом, но только
  из исходящей сети VPS; тест из российского оператора остаётся обязательным.

## Почему не скопированы некоторые части старого проекта

- `app/vpn/marzban.py` использовал HTTP клиент с `verify=False`:
  так нельзя обращаться к чувствительной удалённой панели в production.
- `install_node.sh` проксировал Marzban API наружу на HTTP-порту
  (socat), включая административную аутентификацию. В VPNX3 нет такого
  публичного интерфейса: операции идут через локальный Unix-сокет.
- `fix_reality.sh` заново генерировал X25519-ключи и short IDs при
  исправлении. Это ломает существующие ключи на устройствах. VPNX3
  сохраняет уже выданные ключи.
- В старом скрипте включался UFW без полной проверки активных правил,
  что может заблокировать SSH. Новый edge-установщик этого не делает.

## Безопасная выделенная нода на 443

**Это решение для отдельного VPS/IP с незанятым TCP/443**, не команда для
текущего сервера `194.146.223.104`, где 443 принадлежит админке Caddy.

На новой ноде с Ubuntu и Docker (после клонирования VPNX3 в `/opt/vpnx3`):

```bash
cd /opt/vpnx3
sudo bash scripts/install-vpn-edge-443.sh check
sudo env VPNX3_EDGE_PUBLIC_ADDRESS=НОВЫЙ_ПУБЛИЧНЫЙ_IP \
  bash scripts/install-vpn-edge-443.sh install
sudo bash scripts/install-vpn-edge-443.sh create-ios
sudo bash scripts/install-vpn-edge-443.sh link-ios
```

Последняя команда намеренно **раскрывает секретный импортируемый URI**
в текущем терминале. Не отправляйте его в чаты, логи или тикеты.
Установка, статус и тесты никогда не печатают секретные ссылки сами.

Профили на новой ноде пока управляются **локально**, а не из главной админки
VPNX3. Интеграция удалённой ноды требует отдельного аутентифицированного
канала управления (mTLS или подписанные команды), отзывов, аудита и
проверки, что control plane не может читать приватный ключ REALITY.
Не следует выдавать локальный edge-скрипт за готовую распределённую админку.

Для продакшена добавьте вторую ноду у другого хостера и клиентское
переключение при потере доступности. Никакая одна конфигурация не
гарантирует VPN-подключение из всех операторских сетей РФ.

## Acceptance-условия

1. Доступный порт 443 с внешнего клиента (не только loopback VPS).
2. Валидный импорт `vless://` в используемом приложении iOS.
3. Подтверждённый REALITY handshake и HTTPS через VPN, не только Xray config-test.
4. Работа native Telegram на iPhone с мобильного оператора и Wi-Fi;
   отдельная проверка HTTP `telegram.org` недостаточна.
5. Стабильное переподключение после смены сети и рестарта сервера;
   проверка DNS, IPv4/IPv6 и absence of route leaks.
